# Running a pinned version and ending a run

- Call `termous.desktop_workflows.runs.start` with an explicit version and exactly one target selector: session_id plus connection_generation, or profile_id. Takeover is disabled by default; takeover=true must remain within the user's authorized target and scope.
- The start response returns run_id; Core continues preparation and initiates the global approval flow. In waiting_user_action, the trusted UI handles certificates, host keys, or missing credentials. Do not make trust decisions or supply passwords yourself.
- Each workflow run requires its own control grant; an existing direct-input grant cannot be reused for a script. Before switching from direct control to a script run, release the direct-control grant you acquired. The workflow grant lasts at most 30 minutes and is released after 15 minutes without a qualifying run capture or input. Polling reports and previewing templates do not renew the grant.
- The built-in Agent's start tool keeps waiting until preparation and manual approval finish. While the user's decision is pending, do not start again or end the current Agent Run. For subsequent waits, prefer `wait_workflow_run`: during ordinary execution, each call waits at most 60 seconds; during manual approval, it keeps waiting for Core to report approval, rejection, or expiry without requiring repeated model queries. External clients use after_revision and wait_ms (at most 10000 milliseconds) with `termous.desktop_workflows.runs.get` to wait for changes. An ordinary wait timeout returns only the current state snapshot. **Wait for a terminal state before ending the Agent Run or closing the MCP session.** Ending the caller cancels the workflow run; do not promise that it will continue independently in the background.
- After reading this document, use the run, query, or wait tools directly. Reading documentation, rereading it with refresh, or rediscovering the same tool does not resume execution. If the user says "continue" in a new Agent Run, first query the existing run_id to establish its actual terminal state. A cancelled or interrupted workflow cannot simply be resumed, and its old input grant cannot be restored.
- `termous.desktop_workflows.runs.list` returns paginated summaries. `termous.desktop_workflows.runs.control` can manage only your own runs, with action set to pause, resume, step, or cancel. The user can intervene through the UI at any time; do not automatically reclaim control.
- Closing the page does not cancel a run. A connection created by the run is closed by default if it is still exclusively owned; keep_connection=true preserves it. Pre-existing connections are always preserved.
- Read the report first, then use `termous.desktop_workflows.assets.get` for evidence as needed. Provide run_id, or script_id plus version, to establish the image's relationship to the run or script. A template just confirmed by the current caller and awaiting inclusion in a saved script can be read directly.
- In a report, `steps[].asset_id` identifies screenshot evidence from that run and may differ on each failure; it is not the template referenced by the step. `desktop_workflow_image_missing` means an image did not match or a wait for its appearance or disappearance timed out; it does not mean the template asset is missing. Inspect the failure evidence, then read the version specified by the report to verify the step order and templates. Do not infer a version-binding fault or recreate every template from this error alone.
- An action marked accepted was accepted by the protocol only. Without an assertion, completed means execution finished; it does not verify the intended application result. Do not retry automatically after an uncertain outcome, cleanup failure, or disconnection after dispatch. Observe again and explain what is known to the user.
- Distinguish the report's error_code, cleanup_error, and individual step states. A nonempty cleanup_error alone does not establish that new text or a click was dispatched. Read-only checks may establish which steps were accepted, where execution stopped, and what cleanup remains unconfirmed. If the input or step itself is uncertain, stop subsequent automated actions. desktop_control_stale does not identify who reclaimed control; do not take over again and rerun from the beginning based on a guess.
